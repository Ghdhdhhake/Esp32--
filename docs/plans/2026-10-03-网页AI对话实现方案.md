# 网页 AI 对话 —— 可落地方案（96 KB 堆预算下的选择）

**日期：** 2026-10-03
**前提：** 板子实测 `free_heap = 96 KB`；用户同意**砍掉 BLE、板载 LED、引脚工具箱**
**结论：** 砍掉 BLE 是唯一的胜负手 —— 堆从 96 KB 回到 **约 185 KB**，Flash 从 1078 KB 瘦到 **约 940 KB**。之后 5 个方案全都跑得动，推荐**方案 1**。

---

## 零、前置动作：砍掉 BLE（所有方案共用）

### 改动

| 位置 | 改动 |
|---|---|
| `sdkconfig.defaults` | 删除整个 BLE 配置段（`CONFIG_BT_*` 全部） |
| `sdkconfig` / menuconfig | `CONFIG_BT_ENABLED=n` |
| `main/CMakeLists.txt` | `REQUIRES` 里去掉 `bt` |
| `main/` | 删除 `ble_scanner.c` / `ble_scanner.h` |
| `main/main.c` | 删掉 4 条 BLE 路由和所有调用 |

### 收益（从 map 文件实测，不是估算）

**RAM —— 这才是关键**

| 来源 | 释放量 | 说明 |
|---|---|---|
| 静态 DRAM 预留 | **56,156 B** | `CONFIG_BTDM_RESERVE_DRAM=0xdb5c`。BT 一关，`dram0_0_seg` 起点从 `0x3FFBDB5C` 退回 `0x3FFB0000`，这块直接并入堆 |
| NimBLE 主机任务栈 | 4,096 B | `CONFIG_BT_NIMBLE_HOST_TASK_STACK_SIZE` |
| MSYS / ACL / 事件缓冲 | ~17 KB | MSYS1 12×256 + MSYS2 24×320 + transport 缓冲 |
| GATT 服务 + 广播 + 扫描态 | ~6 KB | |
| `ble_scanner.c` 设备表（30 条） | ~7 KB | 每条含地址/名称/RSSI |
| **合计** | **≈ 90 KB** | |

> **堆：96 KB → 约 185 KB**

**Flash —— 顺带瘦身**

| 模块 | 已链接大小（map 实测） |
|---|---|
| BT 控制器 `libbtdm_app.a` | 80.6 KB |
| NimBLE 主机 | 49.6 KB |
| `ble_scanner.c` | ~10 KB |
| **合计** | **≈ 140 KB** |

> **固件：1078 KB → 约 940 KB**（应用槽 1.5 MB，剩余从 448 KB 变成 ~590 KB）

**顺带的好处（谨慎乐观）**
固件瘦到 940 KB 后，2 MB Flash 里「双 app 槽 OTA」从"装不下"变成"勉强能塞"
（每槽约 988 KB）。但加了聊天功能后固件会回到 1000 KB 以上，**余量只剩几十 KB，不建议现在上 OTA**。

### 代价

- BLE 面板、手机搜 `ESP32-DASH`、蓝牙扫描全部消失
- LED / GPIO / ADC 面板如果也要砍，只省 Flash（几 KB），**对堆几乎没影响** —— 建议**保留**，因为它们是 AI function calling 的执行端，很值钱

## 二、方案 1：板子做 HTTPS 网关 + WebSocket（推荐）

### 架构

```
浏览器 ──WebSocket──► ESP32 ──HTTPS 流式──► LLM API
   ▲                    │
   └── 对话 UI          └── function calling ──► GPIO / LED / ADC
```

### 为什么可行（关键：现成条件比想象中好）

我查了 `sdkconfig`，TLS 客户端的地基**已经全部就位**：

| 配置 | 当前值 | 说明 |
|---|---|---|
| `CONFIG_ESP_TLS_USING_MBEDTLS` | y | esp-tls 已启用 |
| `CONFIG_MBEDTLS_TLS_CLIENT` | y | 客户端已开 |
| `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE` | y | **证书包已启用** |
| `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_DEFAULT_FULL` | y | **200 张公共 CA，现成的** |
| `CONFIG_MBEDTLS_ASYMMETRIC_CONTENT_LEN` | y | 已是非对称缓冲 |
| `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN` | 16384 | 收 16 KB |
| `CONFIG_MBEDTLS_SSL_OUT_CONTENT_LEN` | 4096 | 发 4 KB |
| `CONFIG_ESP_TLS_DYN_BUF_STRATEGY_SUPPORTED` | y | 支持动态缓冲 |

**唯一缺的是 WebSocket**：`CONFIG_HTTPD_WS_SUPPORT` 当前未开，需要打开。

也就是说：**不用装证书、不用调 TLS、不用引新组件**，写代码就行。

### 内存账

| 项 | 峰值 | 稳态 |
|---|---|---|
| mbedTLS 会话缓冲（IN 16K + OUT 4K） | 20 KB | 20 KB |
| TLS 握手临时状态 | ~10 KB | 0 |
| WebSocket 会话 | 4 KB | 4 KB |
| cJSON 构造请求 | 2 KB | 0 |
| **合计** | **~36 KB** | **~24 KB** |

> 185 KB 中占 36 KB，**余 149 KB**，非常宽松。
> 若以后吃紧，把 `SSL_IN_CONTENT_LEN` 从 16384 降到 8192 可再省 8 KB。

### 实现要点

1. **必须流式**。LLM 返回 SSE，`esp_http_client` 用 `esp_http_client_read()` 循环读，
   每读到一块就 `httpd_ws_send_frame()` 推给浏览器。**绝不能整段收完再发**（一次响应几 KB 到几十 KB，会爆堆）。
2. **HTTP 服务器并发**。`esp_http_server` 默认单任务串行处理，WebSocket 长连接会占住。
   需要确认 `CONFIG_HTTPD_MAX_OPEN_SOCKETS`（默认 7）够用，并把轮询式 API 改成按需拉取。
3. **TLS 放在独立任务**，栈 ≥ 8192 B，别在 httpd 任务里做。
4. **超时**：LLM 首 token 可能要 1–3 秒，`esp_http_client` 的 timeout 设 ≥ 15 秒。
5. **API Key 存 NVS**，通过网页表单写入，不要硬编码进源码。

### 优点 / 缺点

- ✅ API Key 只在板子上，不进浏览器
- ✅ 无 CORS 问题，浏览器只管连板子
- ✅ 顺手把 LED/GPIO/ADC 包装成 function calling，网页上就能用自然语言控制板子
- ❌ 代码量中等（300–400 行 C）
- ❌ 板子在链路中间，板子挂了对话就断

## 三、方案 2：浏览器直连 LLM（最快出效果）

### 架构

```
浏览器 ──(fetch)──► LLM API
   ▲
   └── ESP32 只负责返回 HTML
```

### 板子侧改动

几乎为零：加一条 `/chat` 路由，返回一个新的 HTML 页面（存在 Flash，`EMBED_TXTFILES`）。

### 内存账

**+0 KB**（页面在 Flash 的 DROM，走内存映射）

### 唯一的坑：CORS

- **OpenAI 官方 API 不允许浏览器直连**（不返回 CORS 头，故意防止 Key 泄漏）
- 解决办法二选一：
  - **加免费中转**：Cloudflare Worker / Vercel Edge Function，20 行 JS，免费额度完全够个人用
  - **换支持 CORS 的厂商**（部分国内厂商支持）

### 优点 / 缺点

- ✅ 改动最小，当天能跑起来
- ✅ 板子零负担，堆完全不动
- ❌ API Key 暴露在前端 —— **只能自己用，绝不能公开分享链接**
- ❌ 必须加中转或换厂商

---

## 四、方案 3：内网明文 HTTP 中转（板子侧最稳）

### 架构

```
浏览器 ⇄ WebSocket ⇄ ESP32 ──HTTP 明文──► 局域网中转程序 ──HTTPS──► LLM
                                            (PC / 树莓派 / 路由器)
```

### 内存账

| 项 | 峰值 |
|---|---|
| 明文 HTTP 客户端（无 TLS） | ~6 KB |
| WebSocket 会话 | 4 KB |
| **合计** | **~10 KB** |

### 优点 / 缺点

- ✅ 板子侧最简单，没有 TLS 握手抖动、没有证书链解析
- ✅ Key 安全（在中转程序里）
- ❌ 局域网里要常驻一台设备
- ❌ 多一跳，延迟略增

---

## 五、方案 4：本地微型模型 + 云端对话（混合）

在**方案 1** 基础上叠加 `esp-tflite-micro`：

| 项 | 峰值 |
|---|---|
| TLS 会话 + WebSocket（同方案 1） | 36 KB |
| micro_speech 推理 arena（仅监听时占用） | 30 KB |
| **合计** | **66 KB** |

185 KB 中占 66 KB，**余 119 KB**，仍然宽松。

- 本地：唤醒词 + "开灯 / 关灯 / 亮一点" 等短指令，**离线、零延迟**
- 云端：长对话
- 需加 I2S 数字麦克风（INMP441 / ICS-43434，约 10 元）

---

## 六、方案 5：纯本地小模型（不联网）

如果目标只是"板子上有 AI"，不需要真对话：

- `micro_speech` 关键词唤醒（Flash 18 KB / RAM 30 KB）→ 直接控制 GPIO/LED
- 或传感器分类 MLP（Flash ≤50 KB / RAM ≤20 KB）
- 网页只做状态显示

**完全离线可用**，但对话能力为零 —— 只能识别固定几个词。

---

## 七、推荐

| 你的目标 | 选哪个 |
|---|---|
| 板子独立工作、Key 安全、还想用自然语言控板子 | **方案 1** ⭐ |
| 最快看到对话效果、不在意 Key 在前端 | 方案 2 |
| 不想让板子碰 TLS、局域网有常驻机器 | 方案 3 |
| 既要离线指令又要云端对话 | 方案 4 |
| 只要离线固定指令 | 方案 5 |

**我的建议：先做方案 1。** 地基（mbedTLS + 证书包 + esp-tls）全都是现成的，
只差一个 `CONFIG_HTTPD_WS_SUPPORT=y` 和 300 行 C 代码，
而且它顺带把现有的 LED / GPIO / ADC 面板变成了 AI 能调用的工具 —— 这是这个方案最大的附加值。

### 风险提示

| 风险 | 应对 |
|---|---|
| TLS 握手瞬间堆抖动 | 握手前先 `ESP_LOGI` 打一次 `esp_get_free_heap_size()`；必要时把 `SSL_IN_CONTENT_LEN` 降到 8192 |
| HTTP 服务器单任务串行 | WebSocket 长连接会占住 httpd 任务，轮询类 API 要改成按需拉取 |
| 长回答撑爆缓冲 | 强制流式，逐块转发，不缓存完整响应 |
| API Key 泄漏 | 存 NVS，页面不返回明文；网页加个简单的访问口令 |

## 九、实施结果（2026-10-03 已完成并编译通过）

### 9.1 配置变更

`sdkconfig` 与 `sdkconfig.dev` 两份都改了（`tools/build.sh` 实际用的是 **`sdkconfig.dev`**）：

- 删除整个 `# Bluetooth … # end of Bluetooth` 段（323 行）→ `# CONFIG_BT_ENABLED is not set`
- 清理散落在 `Component config` 里的 52 行 `CONFIG_NIMBLE_*` 残留
- `CONFIG_HTTPD_WS_SUPPORT=y`

> ⚠️ 必须**显式写出** `# CONFIG_BT_ENABLED is not set`。只删不写会回落到默认值 `y`。

### 9.2 代码变更

| 文件 | 说明 |
|---|---|
| `main/llm_client.h` / `.c` | 新增。NVS 配置 + OpenAI 兼容 SSE 流式客户端 |
| `main/chat_ws.h` / `.c` | 新增。4 条路由 + 独立 chat 任务 + 6 个工具 |
| `main/device_api.h` | 新增。main.c 与 chat 之间的窄接口 |
| `main/web/chat.html` | 新增。气泡对话界面，18.4 KB |
| `main/main.c` | 删 BLE（头文件 / 4 个 handler / 4 条路由 / init 调用）；加 3 个 device_api 实现；`start_web_server()` 返回 handle；调用 `chat_register()` |
| `main/CMakeLists.txt` | 去 `bt`、去 `ble_scanner.c`；加 `esp_http_client esp-tls mbedtls`；`EMBED_TXTFILES` 加 `chat.html` |
| `main/web/index.html` | 删 BLE 面板（54 行 HTML + 23 行渲染 + 132 行交互 + 1 行 CSS）；头部加「打开 AI 对话」入口 |
| `main/ble_scanner.c` / `.h` | 已删除 |

### 9.3 实测结果

**内存 —— 这是真正的收获**

| 项 | 改动前 | 改动后 | 变化 |
|---|---|---|---|
| `dram0_0_seg` 起点 | `0x3FFBDB5C` | `0x3FFB0000` | BT 预留 56,156 B 归还 |
| 静态 `.data + .bss` | 63,192 B | 57,816 B | **−5,376 B** |
| **开机堆** | **208,328 B** | **269,864 B** | **+61,536 B（+60.1 KB）** |

> 修正：早先按 `0x40000000 − _bss_end` 算成 +62.7 KB 是错的。
> `_heap_end` 实际是 `0x40000000 − _sram1_iram_len`，而含 BLE 时 IRAM 会溢进
> SRAM1 占掉 12 KB。用 map 里的 `_heap_end` 符号同口径对比，真实收益是 **+60.1 KB**。

另外 NimBLE 主机任务栈、MSYS/ACL 缓冲（约 30 KB）是运行时从堆里分配的，现在也不再占用。
**预期 `free_heap` 从 96 KB 涨到约 185 KB**（上板确认）。

**Flash —— 基本持平，和预估的不一样**

| 项 | 变化 |
|---|---|
| 移除 BT 控制器 `libbtdm_app.a` | −80.6 KB |
| 移除 NimBLE 主机 | −49.6 KB |
| 移除 `ble_scanner.c` | −10 KB |
| 新增 mbedTLS TLS 客户端栈 | **+59 KB** |
| 新增 mbedTLS 证书包（200 张 CA） | **+67.4 KB** |
| 新增 `esp_http_client` + `esp-tls` | +19.7 KB |
| 新增 `chat_ws.c` + `llm_client.c` + `chat.html` | +33 KB |
| **净变化** | **+1.8 KB** |

固件 `1,103,968` → `1,105,792` B（1.054 MB），应用槽剩余 **467 KB（30%）**。

> **为什么和文档前面的「−140 KB」预估不符**：之前 mbedTLS 的 TLS 客户端和证书包
> **从未被引用过**，链接器把它们整个丢掉了。现在 `esp_crt_bundle_attach` 一引用，
> 这两块（合计约 126 KB）就全被拉进固件。BT 省下的 140 KB 正好被抵掉。
>
> 结论：**Flash 没有变宽松，但 RAM 实打实多了 62.7 KB** —— 这本来就是我们的目标。

### 9.5 一个值得记住的坑

`tools/build.sh` 写死了 `-D SDKCONFIG=$PROJECT_DIR/sdkconfig.dev` 和 `-B build-dev`，
**不读 `sdkconfig`**。改配置时必须改 `sdkconfig.dev`，否则改了不生效。

另外这台机器上 CMake 首次 configure 花了 **19.7 分钟**（`-- Configuring done (1182.7s)`），
整个全量构建 24.5 分钟。增量构建正常。

### 9.6 上板后需要确认的三件事

1. `free_heap` 是否从 96 KB 涨到约 190 KB
2. 打开 `http://192.168.4.1/chat`，右上角「设置」填 Base URL / API Key / 模型名
3. 发一句「把板载 LED 调成呼吸模式」，看 LED 是否真的开始呼吸，以及工具标签是否出现
